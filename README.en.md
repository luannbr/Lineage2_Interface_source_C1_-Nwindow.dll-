# Lineage II C1 NWindow.dll — source rebuilt in C++

[Português](README.md) · **English** · [Русский](README.ru.md)

A function-by-function rebuild of the `NWindow.dll` of the Lineage II **Chronicle 1 (Harbingers of War)**
client: the native UI DLL (windows, controls, NPC HTML, IME, chat, console). The target is the original build
of 2004-06-25 (TimeDateStamp `0x40DBD452`, Visual C++ .NET 2002, md5 `2dacb6eb…`). The same source builds
three ways:

| CMake target | Output | What it is |
|---|---|---|
| `NWindowDecomp` | `build/bin/Release/NWindowDecomp.dll` | **hook mode**: runs next to the original `NWindow.dll` and replaces every function already rebuilt with a `jmp` to ours |
| `NWindowStandalone` | `build/standalone/Release/NWindow.dll` | **faithful standalone**: the whole `NWindow.dll`, our code only; the reference every test compares with the original |
| `NWindowL2` | `build/l2/Release/NWindow.dll` | **standalone + phase-6 features** (the DLL players get): the same code with `NW_FEATURES=1` and `src/features/` |

## How it works

**Hook mode.** The installer (`tools/install_test.py`) adds an import of `NWindowDecomp.dll` to the original
`NWindow.dll`. Our DLL loads before any original code runs and puts a `jmp` at the entry of every function we
have rebuilt (an `NW_HOOK_*` macro next to each definition, `src/re/NwHook.h`). Everything else is still the
original code. So each new function is tested in the real game, and any of them can be switched off in
`NWindowDecomp.ini` (`[Hooks] Disable=`) to isolate a bug.

**Standalone (phase 5).** With `NW_HOOK_MODE=0` the hook macros are empty and the source builds `NWindow.dll`
on its own: the 178 `UClass` objects (`IMPLEMENT_CLASS`), the globals, the exports at the original ordinals
(`src/standalone/NWindow.def`) and the 7 colour cursors. The engine (`Core.dll`/`Engine.dll`) loads our DLL as
it loaded the original.

**Phase 6 (features).** Features that used to be patched in from outside (the earlier `NWindow_C1` project,
an injected DLL) are source here, in `src/features/`. The decompiled code only holds the call site, in an
`#if NW_FEATURES` block with a `// phase 6: ...` comment; hook mode and the faithful standalone never see it.
Features:

- **Combat log** (system/combat panel over the chat), **BuffTimer** (time left on the buff icons);
- **AutoShot** (automatic soulshot/spiritshot, C3 style), **ManufactureCmd** (`/dwarvenmanufacture`, actions
  37 and 52), **MinimapHotkey** (Alt+M / M), **CacheCleaner** (periodic `FLUSH` + `OBJ GARBAGE`);
- C2-style **craft windows** (shop, recipe book, tree) and the **manufacture balloon**;
- **WindowFix** (windowed mode: movable frame, UI mouse, click filter), **ReturnToLogin** (back to the login
  screen instead of a dead server list);
- **Discord Rich Presence** (talks to Discord's local pipe directly, no SDK);
- **ChatColors** (Interlude's colours for command channel and hero voice), **ItemHoverTip** (the hovered
  item's name in a dark box with the grade symbol).

Settings use no file: what was `LineageWindow.ini` is compiled in (`src/features/NwFeatureConfig.cpp`) and what
the player changes in the game goes to the registry, `HKCU\Software\Lineage2C1\NWindow\<Section>`. The client
protections the author's server uses are a private module and **are not part of this source**.

## Status

- Hook mode: **2,744 of 3,653** functions to rebuild are done (**95.42 %** of the code bytes), none left without
  a reason; what remains is generated by the compiler in the standalone build (scalar deleting destructors,
  `InternalConstructor`, static initialisation). **1,360** have been tested in the game.
  Live count: [docs/PROGRESSO.md](docs/PROGRESSO.md) (generated by `tools/build_db.py`).
- Standalone: links, passes the static checks and the smoke test (output identical to the original, line by
  line) and was tested in the game.
- Phase 6: all the features above are in the source and pass the cycle; the state of each (tested in the game
  or not) is in [docs/notas/Fase6.md](docs/notas/Fase6.md).
- The technical notes (`docs/`) are in Portuguese; code comments are in English.

## Requirements

- Windows, **Visual Studio 2022** with x86 C++ (MSVC v143), **CMake ≥ 3.20**;
- **Python 3** with `pefile` and `capstone` (`pip install pefile capstone`): used by the standalone build
  (cursor extraction) and by every tool;
- **your own Lineage II C1 client**. No game file is in the repository: copy into `orig/` the files listed in
  [orig/README.md](orig/README.md) (the `NWindow.dll` must have the md5 given there);
- for the judges of the full cycle (`verify_hooks.py`, `regcheck.py`, `verify_standalone.py`, `build_db.py`):
  the Ghidra export in `analysis/ghidra/`, recreated by `tools/ghidra/run_export.sh` (Ghidra 11.3.2 and JDK 21;
  paths in the `GHIDRA` and `GHIDRA_JAVA_HOME` variables).

## Build

In a VS 2022 x86 *Developer Command Prompt* (or after `vcvars32.bat`), at the repository root:

```bat
cmake -S . -B build -A Win32
cmake --build build --config Release
cmake --build build --config Release --target NWindowStandalone
cmake --build build --config Release --target NWindowL2
```

The first `--build` makes the hook-mode DLL and the test tools (`nwd_smoke`, `nwd_difftest`, `nwd_craft_test`)
and does not need `orig/`. `NWindowStandalone` and `NWindowL2` need `orig/NWindow.dll`. Option:
`-DNW_FEATURE_LOG=ON` makes `NWindowL2` write `LineageWindow.log` (diagnosis only; a normal build writes no file
at all).

## Install and test

Use a **copy** of the client's `System` folder, never the one you play with.

**Hook mode:**

```bat
python tools\install_test.py --system "C:\...\Lineage II\System - Test"
python tools\install_test.py --system "C:\...\Lineage II\System - Test" --restore
```

The first writes an `NWindow.dll` rebuilt from `orig/NWindow.dll` with the extra import, `NWindowDecomp.dll`
and an `NWindowDecomp.ini` (the `NWindow.dll` that was there is kept as `NWindow.dll.pre-decomp-bak`); the
second puts back what was there. `NWindowDecomp.log` in that folder lists every installed hook. In the `.ini`:
`[Hooks] Enabled=0` keeps all the original code; `Disable=` takes an address (`1000cc40`), a method
(`NCGDevice::DrawText`) or a class (`NCGDevice::*`); `[Debug] Marker=1` draws marks only our code draws (a yellow
line at the top, `#` in the password field), to check that the hooks are live.

**Standalone / phase 6:** close the game, keep the test folder's `NWindow.dll` aside and copy over it
`build\standalone\Release\NWindow.dll` (faithful) or `build\l2\Release\NWindow.dll` (with the features). Just
that file: no `.ini` and no `.log` next to it. To go back, put the original back.

**Full cycle** (build, smoke, judges, standalone, L2, install, database; stops at the first failing step):

```bat
python tools\cycle.py --system "C:\...\Lineage II\System - Test"
python tools\cycle.py --system "C:\...\Lineage II\System - Test" --no-install
```

Pass `--system`, or set `NWD_CLIENT_SYSTEM` (below). The cycle
uses `build/` and copies from that folder the DLLs the loader needs (`Core.dll`, `Engine.dll` and their
dependencies). The game must not be running from that folder for the install step.

**Machine paths.** No tool has a path of the author's machine: a folder outside the repository comes from its
command-line option or from one of these variables (the option wins; a tool that needs one and has neither stops
and names it):

| Variable | Points to | Used by |
|---|---|---|
| `NWD_CLIENT_SYSTEM` | the test client's `System` folder (a copy: the install writes into it) | default `--system` of `install_test.py`, `cycle.py`, `smoke_standalone.py`, `difftest.py`; `verify_hooks.py --log` |
| `NWD_C1_SERVER` | the server's deploy folder (pages in `gameserver/data/html-en`) | `difftest.py`, page set `server` (skipped when unset) |
| `NWD_GHIDRA_HOME` | the Ghidra install (with `support/analyzeHeadless.bat`; `GHIDRA` still overrides it) | `tools/ghidra/*.sh`, `tools/c2/ghidra_census.sh` |

## The judges

The cycle (`tools/cycle.py`) runs all of them, in this order; "green" means the cycle exits with code 0.

| Judge | Command (the cycle adds your `--system` where the tool takes one) | What it proves |
|---|---|---|
| smoke | `build\smoke\Release\nwd_smoke.exe build\smoke_system` | the patched `NWindow.dll` (installed into `build/smoke_system`) loads outside the game and every hook reports `ok` (`NWindowDecomp.log`) |
| verify | `python tools/verify_hooks.py --log build/smoke_system/NWindowDecomp.log` | each of our functions against the original, from the disassembly: stack bytes popped by `ret`, vtable slots and imports called; a difference is accepted only with an explanation in `db/verify_notes.csv` |
| regcheck | `python tools/regcheck.py` | no original caller relies on a register our function may change (the original was built with `/GL`) |
| difftest | `python tools/difftest.py --golden` | pieces of the DLL run outside the game and write the same as the original (`tests/golden/`) |
| standalone: declarations | `python tools/verify_standalone.py --checks source` | our `NW_DECLARE_CLASS` / `NW_CHECK_VTABLE` against the original class table |
| standalone: verify | `python tools/verify_standalone.py --dll build/standalone/Release/NWindow.dll` | PE, resources, exports, classes and vtables equal to the original's, without running it |
| standalone: difftest | `python tools/difftest.py --standalone build/standalone/Release/NWindow.dll` | the same difftest cases on the standalone DLL |
| standalone: smoke | `python tools/smoke_standalone.py --dll build/standalone/Release/NWindow.dll` | loaded the way the engine loads it: 178 classes registered, `ConsoleWnd`/`L2Font` constructed, output equal to the original's |
| l2: craft data | `build\craft\Release\nwd_craft_test.exe` | the craft windows' protocol parser |
| l2: discord presence | `python tools/presence/presence_test.py` | Rich Presence against a fake Discord |
| l2: verify / smoke | `python tools/verify_standalone.py --dll build/l2/Release/NWindow.dll --l2` and `python tools/smoke_standalone.py --dll build/l2/Release/NWindow.dll --l2` | the phase-6 DLL passes the same tests, with exactly the extra classes of `tests/standalone/l2_extras.csv` |
| db | `python tools/build_db.py` | regenerates `db/functions.csv` and `docs/PROGRESSO.md` |

## Layout

```
orig/          binaries of your client (not in git; md5 in orig/README.md)
analysis/      facts extracted from the original (classes, EH, vtables; the exported Core/Engine vtables); analysis/ghidra/ = Ghidra export (generated, not in git)
db/            function database (functions.csv generated) + names, notes and checks written by hand
include/ue2/   declarations of the C1 Core.dll/Engine.dll, checked against the exports
include/nwindow/, src/nwindow/    the decompiled source, one class per file
src/re/        hook-mode runtime (hook installation, log, ini, CRT compatibility)
src/standalone/                   IMPLEMENT_CLASS / IMPLEMENT_PACKAGE, globals, NWindow.def
include/features/, src/features/  phase 6: the features
tests/         reference outputs of the original (golden) and the standalone lists
third_party/ue_import/            .def files of the Core/Engine exports (turned into .lib by the build)
tools/         analysis, generators, installer, judges, cycle
docs/          plan, conventions, progress and technical notes (Portuguese)
```
